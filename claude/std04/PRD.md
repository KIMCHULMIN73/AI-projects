# PRD — 냉장고 사진으로 레시피 추천하기

냉장고 사진 한 장을 올리면 **식재료를 뽑아내고 → 그 재료로 만들 레시피를 추천하고 → 마음에 드는 것을 프로필별로 저장**하는 웹 앱이다.

이 파일은 색인이다. 실제 사양은 단계별 문서와 unit 문서에 있다.

## 단계

| 단계 | 문서 | 하는 일 | 앞 단계에서 받는 것 |
|---|---|---|---|
| 1 | [PRD_step1.md](PRD_step1.md) | 이미지 → 식재료 목록 | (없음) 사용자가 올린 사진 |
| 2 | [PRD_step2.md](PRD_step2.md) | 식재료 목록 → 레시피 | `IngredientList` |
| 3 | [PRD_step3.md](PRD_step3.md) | 프로필 + 레시피 보관함 | `Recipe` |

**단계 경계는 곧 데이터 계약이다.** 각 단계는 앞 단계의 *산출물 JSON*만 입력으로 받고, 앞 단계가 그것을 어떻게 만들었는지 몰라야 한다. 그래야 2단계를 고치는 동안 1단계를 건드리지 않을 수 있고, 1단계 없이 재료를 손으로 입력해 2단계만 개발할 수 있다.

## unit — 여러 단계가 공유하는 사양

각 단계 문서에서 반복될 내용은 여기로 뺐다. 단계 문서는 **참조만** 하고 내용을 복사하지 않는다.

| unit | 무엇을 정하는가 | 쓰는 단계 |
|---|---|---|
| [UNIT_proxy.md](units/UNIT_proxy.md) | 키를 쥔 로컬 서버, 라우팅, 정적 서빙 | 1·2·3 |
| [UNIT_model_call.md](units/UNIT_model_call.md) | OpenRouter 호출·모델 선택·타임아웃·재시도 | 1·2 |
| [UNIT_json_contract.md](units/UNIT_json_contract.md) | 모델에게서 **파싱 가능한 JSON**을 받아내는 법 | 1·2 |
| [UNIT_image_input.md](units/UNIT_image_input.md) | 이미지 받기·축소·data URI 변환 | 1 |
| [UNIT_storage.md](units/UNIT_storage.md) | localStorage 키 규칙·버전·실패 처리 | 1·3 |
| [UNIT_ui_state.md](units/UNIT_ui_state.md) | 화면 상태 전이, 긴 대기, 오류 표시 | 1·2·3 |

## 구조

```
   브라우저 (index.html · app.js)
      │   fetch('/api/vision')  fetch('/api/recipe')
      │   ※ 키를 모른다. 모델 이름조차 모른다.
      ▼
   로컬 프록시 (server.py, 파이썬 표준 라이브러리)
      │   config.py로 키를 읽어 Authorization 헤더를 붙인다
      │   Models 파일에서 모델 ID를 읽는다
      ▼
   OpenRouter API
```

**브라우저는 OpenRouter를 직접 부르지 않는다.** 부르는 순간 키가 화면 소스와 네트워크 탭에 그대로 드러나기 때문이다(CLAUDE.md의 "절대 하지 말 것"). 프록시는 이 제약 때문에 생긴 것이지만 덤이 둘 있다:

- 브라우저가 모델 이름을 모르므로, **모델을 바꿀 때 `Models` 파일만 고치면 된다.** JS는 손대지 않는다.
- 프록시가 정적 파일도 같이 서빙하므로 **CORS 문제가 아예 없다.** 서버도 포트도 하나뿐이다.

## 확정된 결정과 그 근거

바꾸려면 이 표를 먼저 고칠 것. 근거 없이 뒤집으면 같은 실수를 반복한다.

| 결정 | 근거 |
|---|---|
| 로컬 파이썬 프록시를 둔다 | 브라우저에 키를 내려보낼 수 없다. 유일한 대안. |
| 영속화는 **localStorage만** | 사용자 결정. 형제 프로젝트(std02·std03)와 같은 방식이라 서버가 파일을 건드릴 일이 없다. **대가: 브라우저를 바꾸거나 캐시를 지우면 저장한 레시피가 사라진다.** 백업이 필요해지면 3단계 문서의 "나중에 열어 둔 길"을 볼 것. |
| 프로필은 **여러 개**, 화면에서 전환 | 사용자 결정. |
| 프로필은 레시피 생성에 **영향을 주지 않는다** | 사용자 결정. 프로필은 보관함을 나누는 이름표일 뿐이다. 덕분에 2단계는 3단계를 전혀 모르고, 3단계 없이도 2단계가 완결된다. **대가: 알레르기·식단 제한을 자동으로 걸러 주지 못한다.** 나중에 넣는다면 2단계의 `/api/recipe` 입력에 필드를 더하는 방식이 된다(2단계 문서에 자리를 비워 뒀다). |
| 외부 라이브러리·빌드 도구 없음 | 리포지토리 관례. 파이썬은 표준 라이브러리, 브라우저는 vanilla JS. |

## 공통 제약

- **키는 `config.py`를 통해서만 읽는다.** `.env`를 직접 파싱하는 코드를 새로 만들지 말 것.
- 프록시가 OpenRouter 응답을 그대로 브라우저로 흘리지 않는다. 필요한 필드만 골라 보낸다 — 응답에 섞인 내부 정보와 오류 본문이 화면·콘솔에 남지 않게 하기 위함이다.
- 로그·예외를 찍기 전에 `config.redact()`를 통과시킨다.
- 개발 전용 스크립트는 `tools/`에 두고 앱이 로드하지 않게 한다.
- 자동화 테스트 러너는 없다. 각 단계 문서 끝의 **검증 체크리스트**가 완료 기준이다.

## 실측 근거 (2026-09-11, 실제 호출)

PRD의 수치는 추정이 아니라 측정값이다. 프롬프트를 바꾸면 다시 재고 이 표를 갱신할 것(`tools/smoke_test_api.py` 참고).

| 항목 | 값 | 비고 |
|---|---|---|
| 비전 모델 JSON 스키마 강제 | **지원** (`response_format`/`structured_outputs`) | 코드펜스 없이 순수 JSON이 온다 |
| 텍스트 모델 JSON 스키마 강제 | **미지원** | 프롬프트로 요구 + 복구 경로 필요 |
| 비전 1회 (640×420 JPEG) | **18~23초**, 입력 400~570 · 출력 1,800~2,200 토큰 | 추론형이라 출력 토큰이 많다 |
| 텍스트 1회 | **3초**, 출력 ~600 토큰 | 3회 연속 모두 JSON 파싱 성공 |
| 식재료 인식률 | 6개 중 **6개** | 합성 이미지 기준. 실제 사진은 더 어렵다 |
| 분류 정확도 | 프롬프트 개선 전 3/6 → 개선 후 **5/6** | 카테고리의 뜻을 프롬프트에 적어야 맞는다 |
| 이름 문자열 깨짐 | **발생** (`달걀` → `달modification달걀`) | 1단계 문서의 이름 정규화·사용자 수정이 여기서 나왔다 |
