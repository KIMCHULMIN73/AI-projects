# PRD 2단계 — 재료로 레시피 추천하기

> 색인: [PRD.md](PRD.md) · 앞 단계: [PRD_step1.md](PRD_step1.md) · 다음 단계: [PRD_step3.md](PRD_step3.md)

## 목표

1단계가 만든 **재료 목록**을 받아, 그 재료로 만들 수 있는 **레시피 2~3개**를 추천한다.

## 완료 기준

- 재료 목록에서 버튼을 누르면 3초 안팎에 레시피가 뜬다
- 각 레시피가 **가진 재료와 부족한 재료를 구분해서** 보여준다
- 부족한 재료가 적은 순으로 정렬된다
- 1단계 없이도 동작한다 — 재료를 손으로 입력해도 같은 결과가 나온다

**1단계 없이 개발할 수 있어야 한다.** 입력이 `IngredientList` JSON이므로 사진 없이 목록만 만들어 넣으면 2단계를 단독으로 만들고 검증할 수 있다. 20초짜리 비전 호출을 매번 기다리지 않아도 된다.

## 화면 흐름

```
[재료 목록]  ─[레시피 추천] 버튼─▶  (3초)  ─▶  [레시피 카드 2~3장]
    ▲                                              │
    └────────── 재료 고치고 다시 ──────────────────┘
```

재료를 고치고 다시 누르면 **다른 결과가 나온다.** 이것이 이 앱의 핵심 상호작용이다 — 사용자는 "양파를 빼면 뭐가 나오지?"를 시험해 본다. 그래서 재료 목록은 레시피 화면에서도 계속 보여야 한다.

## 데이터 계약 — `Recipe`

3단계가 저장하는 것이 이 JSON이다.

```json
{
  "recipes": [
    {
      "id": "r-2026091110-1",
      "title": "김치 두부 계란찜",
      "summary": "한 그릇으로 끝나는 부드러운 찜",
      "time_minutes": 20,
      "difficulty": "쉬움",
      "servings": 2,
      "uses": ["김치", "두부", "달걀"],
      "missing": ["대파"],
      "steps": ["두부를 깍둑 썬다", "..."],
      "tips": "대파가 없으면 생략해도 된다",
      "generated_at": "2026-09-11T10:05:00+09:00"
    }
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `id` | 프록시가 만든다. 3단계가 중복 저장을 막는 데 쓴다 |
| `uses` | **입력 재료 이름과 정확히 같은 문자열**이어야 한다. 화면에서 대조해 표시하기 때문 |
| `missing` | 사야 하는 재료. 비어 있으면 "지금 바로 가능" 배지 |
| `difficulty` | `쉬움` / `보통` / `어려움` 셋 중 하나 |
| `steps` | 문장 배열. 번호는 화면이 붙인다 |

## API

`POST /api/recipe` → 입력:

```json
{
  "ingredients": [{"name": "달걀", "quantity": "6개"}],
  "count": 3
}
```

**`IngredientList` 통째로 보내지 않는다.** 레시피 생성에 필요한 것은 이름과 수량뿐이다. `confidence`·`needs_review`·`source`는 1단계의 사정이며 모델에게 보낼 이유가 없다 — 프롬프트만 길어지고 모델이 엉뚱하게 해석한다.

> **나중에 열어 둔 자리**: 알레르기·식단 제한을 반영하기로 결정이 바뀌면, 이 입력에 `"exclude": ["우유"]`, `"diet": "채식"`을 더하는 방식이 된다. 지금은 넣지 않는다 — 3단계 프로필은 레시피 생성에 영향을 주지 않기로 확정했다(PRD.md의 결정표).

## 프롬프트

텍스트 모델은 JSON 스키마를 지원하지 않는다. **프롬프트가 계약서다** (→ `UNIT_json_contract`).

```
재료: 달걀 6개, 우유 1L, 당근 3개, 두부, 김치, 양파 2개
이 재료로 만들 요리 3개를 추천하라.

규칙:
- 위 재료를 최대한 쓰고, 꼭 필요한 추가 재료만 missing에 적어라.
- 소금·후추·식용유·물은 어느 집에나 있다고 보고 missing에 넣지 마라.
- uses에는 위 재료 목록의 이름을 그대로 써라. 바꿔 쓰지 마라.
- steps는 한 문장씩, 5~8단계로.

반드시 아래 JSON만 출력하라. 설명·인사말·마크다운 코드펜스 금지.
{"recipes":[{"title":"","summary":"","time_minutes":0,"difficulty":"쉬움",
"servings":2,"uses":[""],"missing":[""],"steps":[""],"tips":""}]}
```

- **"소금·후추·식용유·물은 missing에 넣지 마라"** 가 없으면 모든 레시피에 소금이 부족 재료로 뜬다.
- **"uses에는 이름을 그대로 써라"** 가 없으면 `달걀`을 `계란`으로 바꿔 써서 화면 대조가 어긋난다.
- 온도는 0.3. 실측에서 같은 재료로 3회 호출했을 때 2회가 같은 요리를 냈다 — **다양성이 필요하면 `seed`를 바꿔 호출한다**(이 모델은 `seed`를 지원한다). 온도를 올리는 것보다 안전하다.

## 정렬과 표시

- **`missing`이 적은 순 → `time_minutes`가 짧은 순**으로 정렬한다.
- `missing`이 비면 "지금 바로 가능" 배지를 단다. 이것이 사용자가 가장 먼저 찾는 정보다.
- `uses` 중 입력 재료에 없는 이름이 있으면 조용히 `missing`으로 옮긴다. 모델이 이름을 바꿔 쓴 경우다.

## 하지 않는 것

- 영양 성분·칼로리 계산 (모델이 지어낸다. 숫자는 사실처럼 보여서 더 위험하다)
- 조리 사진 (이미지 생성 모델이 없다 → PRD.md의 모델 표)
- 레시피 저장 (3단계 일이다)
- 알레르기 필터 (결정표 참조)

## 검증 체크리스트

- [ ] 재료 6개를 넣으면 레시피 3개가 3초 안팎에 뜬다
- [ ] `missing`이 빈 레시피에 "지금 바로 가능" 배지가 붙고 맨 위에 온다
- [ ] 소금·후추·식용유가 `missing`에 나오지 않는다
- [ ] `uses`의 이름이 입력 재료 이름과 글자까지 같다
- [ ] 재료를 하나 빼고 다시 누르면 결과가 달라진다
- [ ] 재료를 손으로만 입력해도(1단계 건너뛰고) 동작한다
- [ ] 모델이 JSON을 깨뜨려도 복구 1회 후 `BAD_OUTPUT`이 뜨고 앱이 죽지 않는다
